Selected work

Bank submission engine

Home-loan origination platform serving several South African lenders. I own the integration that submits applications and documents to banks and reconciles their replies. When the platform changed submission vendors, I designed the cutover so in-flight applications finished on the vendor already holding them while new ones routed to the replacement, so nobody resubmitted anything, and onboarding the next lender became a configuration change instead of a code change.

Primary author of 558 of 651 commits. Laravel, PHP, SOAP, MySQL, Docker.

Platform security and infrastructure

Multi-factor authentication and OTP verification across every login surface of a multi-tenant platform, switchable per tenant. Web application firewall rules and rate limiting in production, penetration-test findings tracked through to remediation, and file upload and download paths tightened so tenant documents stop being reachable by anyone who guesses a URL.

AWS Transfer Family over S3 with IAM roles and CloudWatch logging for partner SFTP onboarding. WAF, NGINX hardening, audit logging.

Bank integration service

A service that decides whether a loan application qualifies for a bank's new origination system or must fall back to the legacy one, then routes it and tracks amendments and replies. An application that fails a rule is never rejected. It falls back, and the service reports every reason it did.

Built solo. Laravel, Vue 3, Inertia, Pest. Lint and tests run in CI on every push.

Payment recovery bot

A WhatsApp bot that re-engages customers with unpaid orders and hands over to a human when it cannot help. Most of its tests cover the awkward cases rather than the happy path: webhooks arriving out of order, replies landing on closed conversations, messages from numbers it has never seen, and its own records disagreeing with the provider's.

124 commits, sole author. Laravel, WhatsApp Cloud API, Pest.

Document autofill

Applicants upload payslips, bank statements and offers to purchase; a queued job reads them with AWS Textract and fills the blank fields on the application form so nobody retypes a payslip. A document whose ID number contradicts the applicant's never overwrites anything. It stays a suggestion. Tax figures on payslips are deliberately not suggested at all, because payslips mix monthly and year-to-date numbers, and a confident wrong figure is worse than an empty field. Uploaded documents are treated as data, never as instructions.

AWS Textract, Laravel queues, S3. Shipped 2026.

Contributor. Vue 3, TypeScript, Supabase, CASL.

How I work

A bug report names a symptom. Before I edit anything I find every caller of the code I'm about to touch, because one guard in the shared function is a smaller change than a guard in each of its callers, and fixing only the path in the ticket leaves every sibling path still broken.

Before I touch production data I write the read-only version first: queries anchored on business references rather than remembered row ids, run and read before anything writes. Afterwards I write the check that proves it worked, and that would catch it breaking again later.

Then I write it down. Post-mortems for the failures worth understanding, runbooks for the procedures someone else will have to run at an awkward hour. Knowledge that only lives in my head is a single point of failure.
