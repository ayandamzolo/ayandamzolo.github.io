Reading documents without trusting them

Applicants upload payslips, bank statements and offers to purchase. This reads them and fills in the application, without ever letting a document decide something on its own.

  • Lending platform
  • In production
  • Laravel, PHP, Docker, queues, self-hosted OCR

The bottleneck is somebody retyping a payslip

The figures an application form asks for are already printed on the payslip the applicant just uploaded. So the work is transcription: a person reads one screen and types into another. That is where the hours go, and it is also where the wrong digits come from, because nobody proofreads a number they have typed a hundred times.

The point of this system is that nobody retypes a payslip. Everything below exists because removing that step also removes the human who used to notice when a figure looked wrong.

The documents do not leave the network

OCR runs on a self-hosted container on our own infrastructure, with no third-party API key, so no client document leaves the network to be read. A language model then turns that extracted text into application fields. The split matters: the part that handles the raw document stays inside, and the part that interprets text is the only part that talks outward.

Which model reads which document type was measured, not chosen

I did not pick a model because it was cheaper or because it was better on paper. I ran the document types through both and compared.

The cheaper model dropped names on identity documents. On bank statements it moved the expense totals by more than ten percent between two identical runs, which means the same document read twice gave two different answers, and neither run announced that it was the unreliable one. The stronger model was steadier on both. So the unreliable document types route to the stronger model, and the types where the two models agreed stayed where they were. Preference would have moved everything, or nothing.

Guards pinned to documents that actually exist

The field hygiene guards are pinned to a sweep of over two thousand real documents, so a guard I add has to survive the shapes people really upload rather than the shapes I imagined.

One of them exists because of a name. A guard that strips placeholder words would read Nomvula as the word "None" and quietly blank the field, so the guard has to tell a real name from a placeholder instead of matching on the beginning of the word. That failure is worse than no extraction at all, because an empty field gets asked about and a deleted name does not. Uploaded documents are treated as data throughout, never as instructions.

Two things it refuses to do

  • A document whose identity number contradicts the applicant's only ever suggests. It never overwrites a field, because the likeliest explanation is that the wrong person's document was attached, and that is a question for a human, not a merge.
  • Tax figures on payslips are deliberately not extracted at all. Payslips mix monthly and year to date columns, and a confident wrong figure is worse than an empty field: an empty field gets filled in, a wrong one gets approved.

Nothing ends at "failed"

Every failure path degrades to a weaker route rather than stopping. If the OCR container is unavailable, the model reads the document itself. If there is no model credential, the older engine takes over. The result is a worse suggestion, which a person can still correct, instead of an application stuck behind an error nobody is watching.

Evidence. In production on the lending platform. Model routing is the outcome of a per document type comparison, not a preference: dropped names on identity documents and bank statement expense totals moving by more than ten percent between two identical runs are the measurements it was decided on. Field hygiene guards are pinned to a sweep of over two thousand real documents.
