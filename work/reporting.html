Making the numbers legible

An executive and team dashboard for an internet provider: acquisition funnel, product mix, early life churn and cohort retention, built so each team sees only its own figures.

  • Internet provider
  • 182 commits
  • Vue 3 and TypeScript
  • Supabase on Postgres

  • SQL: materialised views, percentile_cont, generate_series cohorts, plpgsql, row level security

What the page is actually for

Somebody opens a dashboard to decide something: where to spend, which product to push, whether last month's churn was a blip or the start of a pattern. That only works while the numbers are trusted, and trust breaks in a particular way. One figure that turns out to be wrong costs more than ten figures that were never shown, because after it every number on the page gets checked by hand, and then nobody opens the page at all.

So most of the work here is not drawing charts. It is deciding what the page does when it cannot answer.

When the views started timing out

The funnel, the product mix, the early life churn window and the cohort grid are the same question asked four ways: which orders reached which milestone, and when. I built it first as views over the order tables, which is the right first version, because there is no second copy of the truth to keep in step with the first.

Then the views started timing out. Cohort retention is the expensive one: every cohort wants every order's milestone history, and the views were working that history out again on each load.

The fix was to materialise the order milestones underneath rather than to tune each metric on its own. Once a milestone is a row with a date on it, the funnel, the churn window and the cohort grid are all cheap reads of one table, and the next metric someone asks for does not arrive with a new slow query attached.

A failed metric reports the reason

The first version did what most dashboards do when a query falls over: it drew the chart with nothing in it. An empty chart is not a blank space. It is a claim. It reads as zero, or as no customers in this period, and either of those is something a person will act on.

A metric that fails now says what happened, where the chart would have been. The query failed, or you are not permitted to see this, or there is genuinely no data in the period you selected. Those are three different situations and they need three different sentences. A dashboard that lies by omission is worse than one that admits it is broken.

Each team sees only its own figures

Executives see the whole picture. A team sees its own figures and not another team's. That is a permission model rather than a piece of interface state, so the rules live in one definition instead of being restated inside each chart, and the same definition governs what the page renders and what the data layer will hand back. Hiding a card in the front end while the query behind it still answers is not a permission model, it is a curtain.

Two small things that changed how it was read

  • While the figures were still being checked against the source systems, every number carried a caveat chip reading "figures under verification". It came off once they were verified, and not before.
  • The default reporting period is month to date, because that is the question most people have when they open it. A default that matches the question saves a click and prevents a misreading.
