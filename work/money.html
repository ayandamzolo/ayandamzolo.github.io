Money logic, and what happens when it changes

I was the sole author of the discount system on a travel booking platform. The codes were the easy half. What a discount should become after the trip it was applied to has changed is the half that decides whether anyone can trust the total.

  • Travel booking platform, 2024 to 2026
  • Sole author of the discount system
  • Laravel, PHP

Two kinds of discount, one kind of code

A discount is either a percentage off the cart or a cash amount off it. Those two behave differently the moment anything around them moves, so they are separate types rather than one type with a flag. Each code is generated, nine characters, so nothing about a code has to be guessed at or typed from a pattern somebody remembered.

Three things, not one

The obvious model is a discounts table: code, value, conditions, times used. It works until the first booking changes, and then there is nowhere to put the truth, because the row describes the offer and the offer has not changed. The booking has.

So the model splits into three things. The code is what somebody types. The rule is what governs whether that code is allowed to apply here, now, to this cart. The redemption is the record of a code actually having been used, on a specific booking, for a specific amount. Three tables, three responsibilities, and only one of them is a history.

What a rule can say

The rules grew as the business asked for more ways to target an offer. A rule can be geographic, by country and by state. It can be tied to specific products. It can carry a usage limit, or be single use, or be first booking only. It can require a minimum cart value. It can be restricted to certain days of the week. And it can require a minimum number of stops on the trip.

Each of those is a separate condition rather than a special case in one long method, because they arrived one at a time and they get combined in ways nobody predicts in advance.

Refunds, which is the actual problem

A code is applied at the moment of booking, against a cart that existed then. Then the trip is modified. Stops are removed, dates move, products change, the cart value drops below what the rule required in the first place. The question the system has to answer is not "what discount did we give" but "what discount does this booking now deserve", and the difference between those two numbers is money that has to move.

The discount is recalculated against what the booking became, not what it was. That is only tractable because the redemption is separate from the rule. The redemption records what was actually granted, so there is a fixed point to compare against. Without it, recalculating means re-deriving the original grant from a rule that may have been edited since, and a confidently wrong refund is worse than asking someone to check.

Agreeing on the logic before writing it

Discount rules are a business decision wearing an engineering costume. Nobody can review a pricing rule by reading a pull request, so I wrote the business logic document the stakeholders signed off from. It meant the arguments about what a rule should mean happened in a document, where they are cheap, instead of in a refund, where they are not.

On the same platform I worked on commission and payout logic, order import tooling, and duplicate order prevention. The through line is the same: every one of them is a place where the system has to be right about money, and where being quietly wrong costs more than failing.

Evidence. Sole author of the discount system across two years on the platform, 2024 to 2026, in Laravel. The business logic document the stakeholders signed off from is a written artefact, not a recollection.
