Access, and the infrastructure under it

Who can get in, what they can reach once they are in, and how partner files arrive. Most of this work was not requested by a ticket. I found it.

  • Lending platform
  • Security and infrastructure work
  • AWS Transfer Family, S3, IAM, CloudWatch, NGINX

Nobody files a ticket for this

A ticket describes something a person has already noticed. Security gaps are the opposite: nobody has noticed yet, and the day somebody does is the day it has already happened. So most of what follows started with me reading a login path, or a download route, or a build log, and not liking what I found there.

Every login surface, not just the main one

A multi-tenant platform has more than one way in. Multi-factor authentication that covers the front door and not the others is a false sense of security, so one-time passwords went onto every login surface rather than the one most people use.

It is switchable per tenant, because the tenants are separate organisations with their own policies. A single platform-wide setting would have been either too weak for the strictest tenant or an imposition on the rest, and the version that gets turned off everywhere to unblock one client protects nobody.

Sessions that actually end, passwords that actually change

Logging out of one guard while staying authenticated on the other is not a logout, so session invalidation happens on both. Sessions are regenerated as well, so an identifier handed out before authentication cannot be carried across it.

On top of that, password reuse is prevented and a reset can be forced. A forced reset is only worth the disruption if the new password cannot be the old one.

Documents that anyone could reach by guessing

Tenant documents were reachable by URL. Not linked, not advertised, but reachable by anyone who guessed the address, which means the only thing standing between a client's bank statement and a stranger was that nobody had tried. I closed the upload and download paths so authorisation is checked on the document itself, not inferred from the fact that somebody had the link.

The edge

Web application firewall rules and rate limiting run in production, NGINX is hardened, and versions with known vulnerabilities were upgraded rather than noted. Penetration test findings are tracked through to remediation, which is the part that usually gets dropped: a findings list is a description of the problem, and it is very easy to file one and feel finished.

Partners who send files rather than call an API

Not every partner integrates over an API. Some exchange files, and they are going to keep doing that, so the honest answer is to make the file path safe instead of pretending it will be replaced. Secure SFTP onboarding runs on AWS Transfer Family over S3, with IAM roles and CloudWatch logging, and access scoped per partner so no partner can see another's files.

Incoming files are schema validated at the boundary. A file that is wrong should be refused at the door, where there is still somebody to tell, rather than discovered later as bad rows that have already been read by something downstream.

When the data stops arriving

The same work continues underneath, in Redshift and DMS troubleshooting when synchronisation breaks. A sync that fails rarely errors in anyone's face. It just quietly gets older, and everything reading from it keeps answering confidently with yesterday.

The password in the build log

On another team's pipeline I found a database password being written to the CI log. Nothing was broken. The build passed, and it had been passing. That is the shape of most of this work: the system was doing exactly what it had been told to do, and anyone who could read the pipeline had a production credential.

Evidence. Multi-factor authentication and OTP across every login surface of the lending platform, switchable per tenant. Firewall rules and rate limiting in production, penetration test findings tracked to remediation, NGINX hardening. Partner SFTP onboarding on AWS Transfer Family over S3 with IAM and CloudWatch. AWS Certified Cloud Practitioner, 2026.
